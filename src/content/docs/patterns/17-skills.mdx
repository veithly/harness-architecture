## Skill 什么时候该自动触发？

<Verdict tldr="自动触发首先是匹配问题：触发太宽会把无关说明和工具声明带进当前回合，触发太窄又会漏掉真正需要的工作流。本文追踪触发条件、依赖预检、安装扫描与人工确认。描述进入 prompt、工具被声明、运行时权限被授予、文件被安装并跨会话保存，是四个不同动作；这里记录源码观察，不把安装演示当成安全证明。"/>

最难排查的不是 Skill 没有触发，而是用户只提到一个相似词，它就抢先进入上下文，挤占注意力，甚至引出一次不必要的审批。先判断触发是否准确，再讨论文件格式和分发。

本文不做四套产品的功能清单。先看误触发和漏触发的代价，再按需要打开各系统的源码底稿。

## 触发前先分清五层

| 要问什么 | 可验证证据 | 不要混淆 |
| --- | --- | --- |
| 这次请求真的匹配吗？ | `when_to_use`、正负样本、隐式触发策略 | 记录误触发和漏触发，不凭直觉报准确率 |
| 哪些内容会进入 prompt？ | 列表阶段的 `name`、`description`，调用阶段的正文 | 元数据帮助筛选，不等于已执行 |
| Skill 声明要用哪些工具？ | `allowed-tools`、`dependencies` | 声明是输入或约束，不是权限授予 |
| 运行时实际允许什么？ | 宿主 policy、审批、sandbox、OS 运行身份 | 只有运行时强制层决定能否执行 |
| 文件会不会留下来？ | 安装路径、scope、注册表、版本和撤销记录 | 写入磁盘或跨 session 可见是独立的持久化动作 |

这五问比“哪个系统字段最多”更能决定 Skill 是否可维护，也更容易发现误触发带来的实际成本。

## 只在分叉处比较源码

### 需要依赖预检时：Codex

Codex 的 metadata 把 scope、policy、interface 和工具依赖写进结构体。每轮开始前会收集缺失环境变量，再一次性向用户询问。它解决的是中途失败，不等于授予 skill 更高权限。

### 需要把经验变成文件时：Claude Code

`skillify` 不能由模型自行启动。用户触发后，向导分轮确认名称、步骤、成功条件、工具和保存位置，再输出 `SKILL.md`。人工确认发生在持久化之前，这个边界值得保留。

### 需要安装第三方包时：OpenClaw 与 Hermes

OpenClaw 的 scanner 给出规则编号、严重级别、文件、行号和证据片段；安装层据此阻断严重项或提示深审。Hermes 再把来源与扫描结论交叉，决定放行、阻断还是请人确认。

两者都说明一件事：扫描结果是输入，最终信任决策仍需绑定来源和权限；扫描器报错也要在页面上留下可追踪状态。

## 一个可审计的 SKILL.md

先写窄触发器和成功条件，再扩展步骤：

```yaml
---
name: release-check
description: Use when a release candidate needs the repository checks and a recorded diff.
allowed-tools:
  - Bash(git diff:*)
  - Bash(pnpm check:*)
when_to_use: "Only after the user names a release candidate."
---

# Release check

## Success criteria
- The check command exits 0.
- The diff and command output are recorded.
```

把 `allowed-tools` 写到子命令级别；把外部 URL、脚本和凭证声明放进审计清单。没有实际安装实验时，不要声称扫描器效果。

落地前检查：

- 触发描述能否让读者举出一个会触发、一个不会触发的例子？
- 依赖缺失时是否在执行前提示？
- 生成或安装前是否能预览、撤销和定位来源？
- source trail 是否指向固定 commit？

## 四套系统怎样发现与加载 Skills

### Codex · 把 skill 当中台来建

Codex 把「加载一个 skill」拆成八类职责，而不是只做「读文件再拼 prompt」。这些模块分别处理数据、生命周期、渲染、注入、远程同步和依赖预检。

这条流水线被刻意拆成了八块各管一摊的模块：有人负责从磁盘或远程仓库读 SKILL.md，有人负责维护这些 skill 在内存里的注册表和生命周期，有人负责定义「一个 skill 长什么样」的数据结构，有人负责把 SKILL.md 文本渲染成可以拼进 prompt 的片段，有人负责判断这一轮对话该不该把某个 skill 注入进来，有人负责处理远程下载和同步，有人负责检查「这个 skill 声明的环境变量是不是都准备齐了」，还有人负责解析配置层面的可用范围规则。

这种拆分把远程协议、注入策略和依赖类型放在不同模块里，目标是减少改动相互影响。是否真的提升并行开发和维护效率，需要结合依赖图、构建时间和团队工作记录判断。

一份 skill 的「身份证」包含哪些信息呢？我们先看一眼数据结构本身，再回到自然语言解释：

读这份结构时，需要先把几层语义分开。名字和描述属于元数据，列表阶段可以装进 prompt，帮助模型筛选候选；`dependencies` 和 `allowed-tools` 是 skill 对工具的声明或约束，不等于宿主已经授予权限；实际能否调用还要看运行时 policy、审批、sandbox 和操作系统身份。`scope`、路径和插件来源描述可见范围、安装位置和持久化生命周期，也不是执行权限。

把这些信息沉淀在元数据里，意味着 skill 不再只是"一段 prompt"，而更像一个需要单独治理的工作流条目。元数据能帮助选择和审计，但不能替运行时的强制层做决定。

接下来要解决一个常见的工程痛点：很多 skill 实际跑起来需要外部凭证。比如调用 GitHub API 要 `GITHUB_TOKEN`，调用某个内部服务要 `INTERNAL_API_KEY`。如果让模型自己尝试再失败再要环境变量，体验会很糟糕。Codex 的做法是：在每一轮对话开始之前，先扫一遍这一轮可能会用到的所有 skill 的依赖声明，看看必需的环境变量是否都齐了。如果还差几个，就主动向用户弹问，把缺的那几条一次性补齐，再开始正常的对话流程。

已经在本次会话里补过的不重复问。这样的好处是用户最多被打断一次，而且打断的时机是在他要执行任务之前而不是中间。

<SourceBlock path="REF/codex/codex-rs/core/src/skills.rs" lines="59-100" system="codex" summary="进入一轮对话之前，先扫描需要哪些环境变量；已经准备好的跳过，没准备好的统一向用户询问，避免中途失败。">

```rust
pub(crate) async fn resolve_skill_dependencies_for_turn(
    sess: &Arc<Session>,
    turn_context: &Arc<TurnContext>,
    dependencies: &[SkillDependencyInfo],
) {
    if dependencies.is_empty() {
        return;
    }

    let existing_env = sess.dependency_env().await;
    let mut loaded_values = HashMap::new();
    let mut missing = Vec::new();
    let mut seen_names = HashSet::new();

    for dependency in dependencies {
        let name = dependency.name.clone();
        if !seen_names.insert(name.clone()) || existing_env.contains_key(&name) {
            continue;
        }
        match env::var(&name) {
            Ok(value) => {
                loaded_values.insert(name.clone(), value);
            }
            Err(env::VarError::NotPresent) => {
                missing.push(dependency.clone());
            }
            // ...
        }
    }

    if !missing.is_empty() {
        request_skill_dependencies(sess, turn_context, &missing).await;
    }
}
```

围绕这套数据结构，Codex 又做了几个值得借鉴的工程选择。第一，它给 skill 安排了**四级可见范围（scope）**：用户私有、项目共享、组织下发、随产品发布的内置。同一份 SKILL.md 文件，存在不同位置就意味着不同的传播半径：放在用户 home 目录下只有本人能用，放在项目里所有协作者都能用，由组织发布的会通过插件渠道分发，内置的则跟着主程序一起发版本。

第二，它默认所有 skill 都可以被模型隐式触发，除非作者明确声明「这个只能手动调起」。这是触发策略，不是权限策略。第三，用户禁用一个 skill 时不删除它，只是把它标记为「已停用」，留住元数据方便下次重新启用；文件是否继续留在磁盘、何时跨 session 可见，仍由安装和注册流程决定。

第四，为了避免每次用户输入命令都先调一遍语言模型做意图识别，它会先用文本特征做一轮本地匹配（即源码中的 `detect_implicit_skill_invocation_for_command` 函数，根据命令名直接反查能命中哪些 skill），能本地命中的就不再绕一圈大模型。这四个选择叠起来，构成了一种「产品化」的 skill 心智：可见范围像目录可见性，启停像应用开关，触发像快捷键，分发像应用商店。它们仍不等于运行时授权。

### Claude Code · 把"用户愿意写"放在第一位

Claude Code 把重点放在 authoring 体验上。它的设计假设是：用户可能不愿从零写 SKILL.md，却愿意整理刚完成的流程。为此，它内置十几个 skill 作为工具和样例；这个假设是否成立，仍需要完成率和回访数据。

其中一个关键例子是 `skillify`，即用来生成 skill 的 meta-skill。它的用途是把用户刚刚和模型完成的一次对话，转成可复用的 SKILL.md。

它不会一次性把所有问题抛给用户，而是把整个抽取过程拆成四轮简短的多选式交互：先让用户用一句话给"刚才到底在做什么"定个性，再帮用户把流程拆成有顺序的几步并请用户确认，再列出会话里实际用过的工具让用户勾选哪些应该写入声明，最后问一句"下次再触发这个 skill 时，你希望它直接在主对话里跑还是单独开一个子进程跑"。向导生成的是文件和元数据；工具声明、宿主运行时权限、sandbox 和是否跨 session 保存仍要分别由安装与执行层确认。

四轮交互把每次需要确认的内容限制在一个小问题里。这个设计意图是降低填写负担，但源码没有公开完成率或对照实验；是否优于单页表单，需要用产品自己的流程数据验证。

下面是四轮向导背后的 prompt 模板。它先分析会话，再按四个步骤询问用户，最后生成一份 SKILL.md 草稿；阅读重点是交互顺序和输出边界。

SKILL.md 输出格式（skillify 引导生成的标准）：

```markdown
---
name: {{skill-name}}
description: {{one-line description}}
allowed-tools:
  {{list of tool permission patterns observed during session}}
when_to_use: {{detailed description of when Claude should automatically invoke this skill, including trigger phrases and example user messages}}
argument-hint: "{{hint showing argument placeholders}}"
arguments:
  {{list of argument names}}
context: {{inline or fork; omit for inline}}
---

# {{Skill Title}}

## Inputs
- `$arg_name`: Description

## Goal
Clearly stated goal.

## Steps
### 1. Step Name
**Success criteria**: REQUIRED on every step.
```

这套设计里有几个细节值得反复琢磨。

一个是模板要求触发描述以 `Use when...` 开头，并给出触发短语和样例用户消息。在这条隐式触发路径里，描述是模型选择 skill 的主要输入之一。具体描述和负面边界是否能减少误触发、漏触发，应当用本站自己的标注请求集验证；源码没有给出通用准确率。

另一个是**每一步骤都要写「判定成功的标准」**。skill 通常包含多个子步骤；若模型不知道一步是否完成，可能反复尝试或继续推进。把验收条件写在步骤旁边，相当于为每一步提供检查点。

还有一个是**把工具声明细化到子命令**。一份用于发版的 skill 可以只声明 `git cherry-pick`、`gh pr` 等必要命令，再由宿主运行时强制执行。窄声明有助于缩小误用面，但如果 runtime policy 不读取或不执行它，frontmatter 本身不会形成安全边界。

最后还有一个实用的开关：**inline 还是 fork**。inline 意思是这个 skill 直接在主对话里跑，用户看得见每一步，可以在中间介入。fork 意思是把它丢到一个子进程或子 agent 里跑到底，主对话只看一份汇总结果。前者适合需要人盯着的流程（比如冲突需要人来解的 cherry-pick），后者适合干净的、跑完直接交付的流程（比如写一段 changelog），可以让主对话保持简洁。

### OpenClaw · 把 skill 当软件包来管

OpenClaw 看 skill 的角度跟前两家又不一样。它把 skill 视作"会被下载、被解压、被执行的第三方代码"，于是按软件供应链的标准来处理它：从下载、解压、静态扫描到安装上线，每一步都有审计痕迹和回退路径。

这条流水线的第一关是**静态扫描器**。安装 skill 时，扫描器读取支持的文件类型并套用对应规则，例如动态执行、硬编码凭证和提示注入模板。每条命中记录规则编号、文件、行号、证据片段和严重程度，供安装流程生成风险清单。未被扫描的文件类型和规则之外的行为仍是盲区。

扫描的结果如何参与安装决策？OpenClaw 没有"出现一条警告就拒绝"这种粗暴策略，它把不同严重级别对应到不同响应：发现严重问题就直接拒绝并在终端上列出具体文件和行号，发现一般可疑模式就提示用户运行更深入的安全审计命令查看细节，扫描器自己出异常也不会卡住安装，但会建议用户事后跑一次深度审计来补检查。这样的设计在"严格安全"和"用户能装得动"之间做了一个相对克制的平衡。

```ts
async function collectSkillInstallScanWarnings(entry: SkillEntry): Promise<string[]> {
  const warnings: string[] = [];
  const skillName = entry.skill.name;
  const skillDir = path.resolve(entry.skill.baseDir);

  try {
    const summary = await scanDirectoryWithSummary(skillDir);
    if (summary.critical > 0) {
      const criticalDetails = summary.findings
        .filter((finding) => finding.severity === "critical")
        .map((finding) => formatScanFindingDetail(skillDir, finding))
        .join("; ");
      warnings.push(
        `WARNING: Skill "${skillName}" contains dangerous code patterns: ${criticalDetails}`,
      );
    } else if (summary.warn > 0) {
      warnings.push(
        `Skill "${skillName}" has ${summary.warn} suspicious code pattern(s). ` +
        `Run "openclaw security audit --deep" for details.`,
      );
    }
  } catch (err) {
    warnings.push(
      `Skill "${skillName}" code safety scan failed (${String(err)}). ` +
      `Installation continues; run "openclaw security audit --deep" after install.`,
    );
  }
  return warnings;
}
```

这条流水线还缓存扫描结果，并按文件大小和修改时间判断是否失效，以减少未修改文件的重复扫描。内置 skill 与用户安装的工作区 skill 走不同审计路径，避免两者相互阻塞。解压第三方包时保留文件落点日志，便于事后核对安装内容。

### Hermes · 把信任当作决策入口

Hermes 把 skill 系统的核心问题归结为一句话：**信任问题**。它认为，一个 skill 装不装，关键不在于代码里有几行可疑的字符串，而在于"这东西从哪儿来"和"扫描看到了什么"这两个维度的组合。

它先按"来源（trust level）"把 skill 分成四类：跟主程序一起发版本的内置 skill 是 `builtin`，来自 OpenAI、Anthropic 这类官方仓库的是 `trusted`，来自社区或者市场的是 `community`，由模型在对话过程中自己生成出来的是 `agent-created`。再按扫描结果给每个 skill 一个判决（verdict）：要么 `safe`，要么 `caution`，要么 `dangerous`。

这两个维度交叉起来，正好形成一张四行三列共十二格的决策表（即下方代码中的 `INSTALL_POLICY` 字典），每一格上写着这种组合下该放行、阻断、还是应交由用户拍板。

<SourceBlock path="REF/hermes-agent/tools/skills_guard.py" lines="37-49" system="hermes" summary="把来源是什么和扫到了什么两个维度叉成一张 4×3 的决策表，每一格直接写明这种组合下是放行、阻断还是交由用户拍板。">

```python
TRUSTED_REPOS = {"openai/skills", "anthropics/skills"}

INSTALL_POLICY = {
    #                  safe      caution    dangerous
    "builtin":       ("allow",  "allow",   "allow"),
    "trusted":       ("allow",  "allow",   "block"),
    "community":     ("allow",  "block",   "block"),
    "agent-created": ("allow",  "allow",   "ask"),
}

VERDICT_INDEX = {"safe": 0, "caution": 1, "dangerous": 2}
```

</SourceBlock>

这张表里有两处安装策略值得看。「受信来源 + 危险特征」这一格是阻断：即使来自官方仓库，扫出明确危险代码也不安装。「模型自己写的 skill + 危险特征」这一格则交由用户拍板（ask）。它们分别处理来源信任和人工确认，不代表安全覆盖率或运行时授权。

除了这套信任机制，Hermes 还把渐进式披露落到安装和加载路径：所有 skill 都放在用户 home 下的统一目录，并对元数据设置字符上限，名字 64 个字符、描述 1024 个字符。它们是该实现的 schema 限制，不是跨 agent 的通用标准。

1024 字符对应多少 token 会随 tokenizer、语言和模型变化，不能当固定换算或容量保证。执行体（可能比元数据长得多的 SKILL.md 内容）只在模型决定调用某个 skill 时加载。

<SourceBlock path="REF/hermes-agent/tools/skills_tool.py" lines="28-100" system="hermes" summary="一份对外兼容、对内自由扩展的 SKILL.md 元数据规范：名字和描述都设了字符上限，方便列表阶段大量装载；可选字段管平台、依赖和扩展元数据。">

```python

    ---
    name: skill-name              # Required, max 64 chars
    description: Brief description # Required, max 1024 chars

                                  #   Valid: macos, linux, windows

# All skills live in ~/.hermes/skills/ (seeded from bundled skills/ on install).
HERMES_HOME = get_hermes_home()

# Anthropic-recommended limits for progressive disclosure efficiency
```

</SourceBlock>

这种 schema 设计与 `agentskills.io` 的公开字段对齐，目标是让多个 runtime 有机会读取同一份 SKILL.md；实际兼容范围仍要按各 runtime 的 parser 验证。它同时保留 `metadata.hermes` 扩展位，存放标签和关联 skill 等实现特有信息。

## 最常见的四个误区

### 误区 1：skill 写得越长越好

很多人写 skill 的第一反应是把所有细节都铺出来：两千行 prompt、三十个步骤、每个步骤再列十几条注意事项。这样会增加模型读取和维护成本，也可能让执行路径变得难以检查。较易维护的写法通常先说清楚"什么时候触发"和"判定成功的标准"，再按需暴露执行细节；具体长度仍应通过任务测试决定。

前面提到的「渐进式披露（progressive disclosure）」（列表阶段只看几百字的描述、真要执行时才把完整内容装进 prompt）正是为了避免这种"越多越好"的错觉。

### 误区 2：自动触发 = 把所有 skill 全部装进 system prompt

为了让模型"能自动用上"所有的 skill，一种简单粗暴的做法是启动时把每个 SKILL.md 都拼进 system prompt。更稳的做法是分两阶段：开机时只让模型看到一份由名字和短描述组成的目录；只有当模型决定调用某个 skill 时，才把正文加载进来。目录大小、缓存和延迟要在目标 provider 上实测，不能从假设的文件数量推算固定节省。Codex 还在这之上加了一层过滤，只把当前用户、当前产品形态下被允许隐式触发的那部分 skill 放进目录，避免目录本身也成为噪音。

### 误区 3：把工具权限开成"允许 Bash"

`allowed-tools` 写在 frontmatter 里，并不等于 skill 获得了 Bash，更不等于 root。它只是声明或约束，是否能执行由宿主的 tool policy、审批、sandbox 和 OS 运行身份共同决定。正确的做法是把声明收敛到具体子命令，例如 `git cherry-pick`、`git status` 或少数 `gh pr` 操作，并在运行时再次强制；否则窄声明也只是文档。

Codex 还用结构化字段声明依赖：它让系统提前知道需要哪类工具、传输协议或端点，但依赖预检仍不授予权限，也不替代执行时的拒绝路径。

### 误区 4：所有来源的 skill 一视同仁

有人会觉得「反正都是 SKILL.md，装上就跑」。但从内置 skill、官方 skill、社区 skill 到模型自己写的 skill，来源和风险并不相同。第三方 skill 在没有审查的情况下执行，会扩大供应链风险。Hermes 的十二格信任表和 OpenClaw 的静态扫描器都把**「来源 + 风险」纳入安装决策**：在 Hermes 的矩阵中，社区来源遇到 caution 会阻断，模型创建且 dangerous 则交由用户确认；具体策略以实现代码为准。

在该矩阵中，明确的 dangerous 模式连 trusted 来源也会阻断。两层防御分别处理内容特征和来源信任，不能替代运行时权限与人工复核。

## 落地前的决策清单

是否需要为你的 agent 引入 skill 子系统，可以用下面这七个问题自检：

1. **这个流程是不是反复发生？** 如果某种工作流（比如把修复挑到发版分支、写发版说明、跑代码评审）每周都要做好几次，那它值得沉淀；如果只是某次临时任务，写一份 prompt 模板就够，没必要单独建一份 skill。
2. **你的用户能写 markdown 吗？** 工程师团队大多能直接写 SKILL.md；面向非工程师用户的产品通常需要提供"从一次会话沉淀成 skill"的向导，再用完成记录验证它是否真的降低 authoring 负担。
3. **是否需要一个 skill 市场或分发渠道？** 如果只是内部使用，本地文件和随产品发布的内置 skill 可能就够；如果用户能从外部安装 skill，应配套来源标签和静态扫描，并明确安装失败与复核路径。
4. **是否希望模型自己判断何时调用 skill？** 隐式触发体验更顺滑，但要求每份 skill 的触发描述写得很具体；如果做不到，老老实实让用户用 `/name` 这种显式命令调起反而更稳。
5. **skill 是否会依赖外部凭证或工具？** 如果会，可以在元数据里明示依赖，让 agent 在执行前检查环境变量和命令；是否改善成功率要按 provider、凭证流程和任务记录验证。
6. **执行时是否需要用户中途介入？** 需要介入的流程更适合在主对话里直接跑；自包含的、能跑到底的流程更适合丢到子进程里，避免大量工具调用占满主对话上下文。
7. **skill 怎么产生？** 如果作者愿意手写，提供模板和样例就够；如果希望用户在会话后留下过程，就需要引导式向导，并用完成率与回访数据评估投入。

不要按回答「是」的数量直接决定是否引入完整子系统。流程稳定但不需要外部安装时，可以先用模板、显式命令和少量示例；只有当触发、依赖、分发或审计成为重复问题时，再分别增加对应组件。

### 十道问题

<details>
<summary>**Q1 · 概念**：skill 跟 prompt template / tool / agent 的本质区别是什么？</summary>

四个概念，颗粒度从细到粗：

**tool**: 单次原子操作。bash / file_read / git_status。无状态，单次调用，返回结果。
**prompt template**: 字符串模板 + 变量。用户主动填变量调起。无 trigger 机制，无 metadata。
**skill**: 工作流 + 触发条件 + 依赖。SKILL.md + frontmatter。模型可以隐式调起，文件可以带 `allowed-tools` / `dependencies` 声明。
**agent**: 独立运行循环 + 多 tool 协同 + 持久状态。有自己 system prompt + tool set + memory。

**为什么需要 skill 这一层？**

prompt template 太弱（没 trigger），agent 太重（每次 spawn 都是新进程）。skill 在中间：

- 比 prompt template 多了「模型自己决定何时用」的能力（when_to_use）
- 比 agent 轻量得多（不开新进程，共享主 agent context）
- 把「反复出现的任务」沉淀下来，下次模型见到 trigger 就自动套用

**实际形态**：

- `cherry-pick-to-release`: 频繁且步骤多，适合沉淀为 skill
- `write-changelog`: 半频繁，skill 或 prompt template 都行
- `git status`: 单步，是 tool
- `data-scientist`: 独立人格 + 长状态，是 agent

**追问**: "skill 能调用 tool 吗？" 可以发起工具请求。skill 是 prompt + 工具声明 + `when_to_use`；请求最终仍要经过宿主 runtime policy、审批和 sandbox，不能只看文件里的 tool list。

**追问**: "skill 跟 sub-agent 区别？" sub-agent 开新进程 + 独立 context window，skill 共享主 agent context（除非 `context: fork`）。

**源码**: `claude-code/src/skills/bundled/skillify.ts` + [`codex/codex-rs/core-skills/src/model.rs`](https://github.com/openai/codex/blob/f27cf9db0974d344d78e7e0b47e7c812776b1395/codex-rs/core-skills/src/model.rs).
</details>

<details>
<summary>**Q2 · 概念**：Codex 为什么把 skill 拆成 8 个独立 crate？</summary>

`core-skills` 16 个文件分为 8 类职责：

- **loader**: 从 disk / remote 读 SKILL.md
- **manager**: skill 生命周期管理（注册 / 解绑 / 失效）
- **model**: SkillMetadata / SkillScope / SkillPolicy 等数据类型
- **render**: SKILL.md 渲染成 prompt 片段
- **injection**: 决定何时把 skill 加入当前 turn 的 prompt
- **remote**: 远程 skill 安装 / 同步
- **env_var_dependencies**: env var 检查 + 缺失补齐
- **config_rules**: SkillPolicy 配置规则解析

**为何要拆得这么细？**

1. **职责单一**: loader 只管读取，不管缓存（cache 由 manager 处理）
2. **测试隔离**: 8 个 crate 各自 mock 各自的依赖
3. **编译速度**: 改 render 不会重新编译 remote

<summary>**Q3 · 架构**：Hermes 的 4 trust × 3 verdict = 12 格 INSTALL_POLICY 怎么工作？</summary>

矩阵：

```python
INSTALL_POLICY = {
    "builtin":       ("allow",  "allow",   "allow"),    # safe/caution/dangerous
    "trusted":       ("allow",  "allow",   "block"),    # openai/anthropic
    "community":     ("allow",  "block",   "block"),
    "agent-created": ("allow",  "allow",   "ask"),
}
```

**4 个 trust level**:
- `builtin`: Hermes 自带，bundled 在 source
- `trusted`: 来自 openai / anthropic 等已审核 vendor
- `community`: 第三方 marketplace
- `agent-created`: 模型自己写的

**3 个 verdict**:
- `safe`: 静态分析没问题
- `caution`: 有可疑 pattern（不一定恶意）
- `dangerous`: 明确高风险（curl + secret, sudo, etc.）

**12 格 = 4 × 3 决策**:

trusted + safe = allow（信任源 + 静态干净，直接装）
trusted + dangerous = block（信任源也不能装危险 skill）
community + caution = block（陌生源 + 可疑 pattern，拒）
agent-created + dangerous = ask（请用户拍板：毕竟模型自创，可能被诱导）

**为何不只用 verdict 或只用 trust？**

只 trust: 信任来源就当全开，但可信源也可能传错文件
只 verdict: 静态扫描有 false positive / negative，无法区分「这是 vendor 真意」vs「这是注入」

**12 格矩阵的精妙**：

`trusted + dangerous = block` 这条最有意思。openai 自己的 skill 都不能带 dangerous pattern，强制 vendor 自我约束。

`agent-created + dangerous = ask` 也精妙：模型可能在攻击者诱导下写恶意 skill，让用户决策。

**实际工程**:

```python
def install_decision(level, verdict):
    return INSTALL_POLICY[level][VERDICT_INDEX[verdict]]
```

这段函数只是查表并返回安装决策；运行时是否能执行仍由安装流程、tool policy、审批和 sandbox 决定，不能据此声称零开销或“编译期全检查”。

**追问**: "怎么决定一个 skill 是哪个 trust？" 看安装来源：
- bundled 目录 → builtin
- vendor URL 白名单 → trusted
- 用户主动从 URL 装 → community
- 模型自己 write_file 创建 → agent-created

**追问**: "矩阵不够细怎么办？" 先用真实安装记录补充来源和扫描结论，再决定是否增加 trust level（enterprise / paid）。Hermes 的 12 格是当前实现的决策表，不等于覆盖率证明。

**源码**: `hermes-agent/tools/skills_guard.py:INSTALL_POLICY + VERDICT_INDEX`.

<summary>**Q4 · 概念**：progressive disclosure 在 skill 系统里怎么应用？</summary>

Progressive disclosure = 「先给摘要，需要再加载详细」。Hermes 的 `MAX_NAME_LENGTH=64` + `MAX_DESCRIPTION_LENGTH=1024` 是该实现的 schema 限制，不是所有 agent 的通用标准。

**两阶段加载**:

**阶段 1（列表）**: 只加载 metadata
- name（≤64 char）
- description（≤1024 char）
- platforms / prerequisites

列表阶段的 metadata 会进入 prompt；总占用取决于 skill 数量、实际描述长度和宿主的列表格式。

**阶段 2（调用）**: 加载 SKILL.md 全文
- prompt body
- 例子代码
- detailed steps

只有当模型决定调起这个 skill 时，才把正文加载到 prompt。工具声明可以在此之前被解析来做候选筛选或依赖预检，但它们不授予运行时权限；实际执行仍由宿主 policy、审批和 sandbox 决定。

不要用假设的 skill 数量和平均字数推出固定的 token 节省。应在目标 provider 上记录列表阶段和调用阶段的实际 prompt、缓存与延迟。

**为什么 64 / 1024 这两个数？**

- 64 char name: 一行命令行可见 + 屏幕宽度友好
- 1024 char description: token 数取决于 tokenizer，不能把字符数换算成固定的上下文容量

Hermes 源码使用这两个上限；其他运行时是否接受相同字段，需要单独核对其 schema。

**对比 Codex**:

Codex 的 `SkillMetadata` 也走 progressive disclosure：
- `short_description`: 列表显示用
- `description`: 调用时用
- full SKILL.md: 进 prompt 用

**实现要点**：

```python
def list_skills():
    return [(s.name, s.description) for s in all_skills]

def load_skill(name):
    return read_file(f"skills/{name}/SKILL.md")
```

简单粗暴。复杂的可以加 LRU cache。

**追问**: "1024 char 不够描述复杂 skill 怎么办？" description 只写「做什么 + 何时用 + key trigger phrases」。复杂内容进 SKILL.md body。

**追问**: "name 64 char 怎么命名？" `kebab-case`, 描述性. `cherry-pick-to-release`, `write-changelog-md`, `find-failing-tests`.

**源码**: `hermes-agent/tools/skills_tool.py:MAX_NAME_LENGTH + MAX_DESCRIPTION_LENGTH`.

<summary>**Q5 · 概念**：Claude Code 的 skillify 4 轮 AskUserQuestion 在引导什么？</summary>

skillify = 「把刚才这个 session 的工作沉淀成一个 skill」。4 轮交互:

**Round 1**: 做什么任务？
- 让用户用一句话总结刚才在做的事
- 这会变成 skill.description

**Round 2**: 什么场景触发？
- 让用户列出「下次什么时候我想再用这套流程」
- 这会变成 skill.when_to_use

**Round 3**: 需要哪些 tool？
- 列出 session 中实际用过的 tool（bash / file_edit / git_status）
- 用户勾选，变成 skill.allowed-tools

**Round 4**: inline 还是 fork？
- inline = 跟主 agent 共享 context（适合需要用户介入的）
- fork = 跑在 subagent 里（适合自包含的）

**最后输出**:

```yaml
---
name: <Round 1 输出 slug化>
description: <Round 1 输出>
when_to_use: <Round 2 输出>
allowed-tools: <Round 3 勾选>
context: <Round 4 选择>
---

<Round 1 + session 总结自动 prompt 体>
```

**为什么 4 轮 + AskUserQuestion 不是一次问完？**

- 一次问多个问题会让表单变重
- 分轮只处理一个决定，便于用户逐步确认；完成率要用自己的流程记录验证
- AskUserQuestion 提供选项，减少打字
- session 上下文自动填默认值（allowed-tools 自动列出已用 tool）

**为什么不让模型自己抽？**

- 触发条件（when_to_use）只有用户清楚
- inline / fork 是 ux 选择，模型猜不准
- 用户参与 = 用户对生成的 skill 有 ownership，未来真会用

**证据边界**：

源码注释提到 skillify 的内部评测，但没有公开样本、流程或汇总方式。这里把向导视为一种降低填写负担的设计，不把来源方的完成率主张外推成通用结果。

**对比其他系统**:

- Codex 没 skillify，要手写 SKILLS.md
- OpenClaw 走 skills-install 装外部 skill，不沉淀本地 session
- Hermes 偶尔在 agent-created 路径下让 agent 自己写，但没 UI 引导

Claude Code 的 skillify 是这组源码里一个有辨识度的选择；是否适合你的产品，要看用户是否愿意在会话结束时确认触发边界和持久化位置。

**追问**: "怎么让 skillify 自己抽 trigger phrase？" 让 Claude 读 session 抽出 top 3 trigger phrase candidate，再让用户选 / 修。半自动。

**追问**: "skillify 出的 skill 怎么 review？" eval 跑一遍，看新 skill 触发后输出跟用户期望对齐没。

**源码**: `claude-code/src/skills/bundled/skillify.ts:22-90`.

<summary>**Q7 · 概念**：OpenClaw 的 skill-scanner 8 种扩展名是哪些？为什么这么选？</summary>

OpenClaw `skill-scanner.ts` 扫描的扩展名：

`.ts`, `.tsx`, `.js`, `.jsx`, `.json`, `.md`, `.yml`, `.yaml`

**为什么这 8 个？**

skill 包通常包含:
- SKILL.md（必备）
- TS / JS 脚本（执行体）
- JSON / YAML（配置）
- 其他 MD（文档）

**扫描内容**:

每个文件按扩展名匹配 danger patterns:

- `.ts / .tsx / .js / .jsx`: 扫 `eval`, `Function()`, `child_process.exec`, `require('child_process')`, 直接 IO 等
- `.json / .yml / .yaml`: 扫硬编码 secret、可疑 URL
- `.md`: 扫 prompt injection pattern（跟 memory scan 类似）

**严重级别 3 档**:

- **critical**: 直接 block 装
- **warn**: 警告用户，需确认
- **info**: 记录但不打断

**对比 Hermes 的扫描**:

- Hermes: 11 个 regex pattern + 10 个 invisible unicode
- OpenClaw: 多文件类型 + 3 级严重 + 5000 entry cache

OpenClaw 的扫描路径覆盖多文件 skill 包；Hermes 的示例集中在单文本记忆。是否适合 marketplace 或 inline content，要看安装格式和 threat model。

**5000 cache 有什么用？**

源码给出的是缓存条目上限，不包含本站的扫描耗时或内存测量；不要把 5000 条推导成 50ms 或 50MB。实际成本应在目标机器上记录。

**追问**: "Python skill 怎么扫？" 加 `.py` 扩展名 + Python 特定 pattern（`exec`, `eval`, `__import__`, `subprocess.run`).

**追问**: "Binary 文件呢？" 默认 skip，或单独扫 file header 看是不是可执行。不深入。

**追问**: "scanner 怎么不被绕过？" 不能完全防。攻击者可以 obfuscate code（base64 / 拆字符串）。scanner 只能覆盖规则库能表达的风险，仍要结合来源、人工确认和运行时隔离。

<summary>**Q8 · 概念**：context: inline vs fork 怎么选？</summary>

Claude Code 的 SKILL.md 有 `context: inline | fork` 字段：

**inline**: 跟主 agent 共享 prompt
- skill 加载到主 agent 的 prompt 里
- skill 请求的工具仍受主 agent 的 runtime policy、审批和 sandbox 约束
- skill 结果直接进主对话
- 用户能看到 skill 执行过程

**fork**: 跑在 subagent (Task) 里
- spawn 一个新 agent，独立 prompt
- 新 agent 完成后返回汇总结果
- 主 agent 只看到结果，不看过程
- 用户看到主 agent 的「我让 subagent 跑了 skill」

**inline 适合**:

- 需要用户介入的工作流（cherry-pick 中途可能 conflict 要 resolve）
- 跟主 agent 上下文紧密耦合的（continue what we were doing）
- 单次执行短，且用户可能随时改方向

**fork 适合**:

- 自包含工作流（write changelog 跑到完，主 agent 不需要参与）
- context 污染严重的（要大量 tool call 不想堆到主对话里）
- 长执行，且主对话不需要逐步介入
- 并行的（同时跑多个 review，每个 fork 一份）

**举例**:

| skill | context | 理由 |
|-------|---------|------|
| cherry-pick-to-release | inline | conflict 要用户解 |
| write-changelog | fork | 自动跑到底 |
| review-pr | fork | 长 context，避污染 |
| add-tests | inline | 用户可能改方向 |

**对比 Codex / OpenClaw**:

Codex 没有 inline / fork 这样的显式字段：它通过 `SkillScope`（可见范围）和 `SubAgentSource`（这个 skill 是否要派生独立 subagent 跑）这两个字段隐式决定。
OpenClaw 走 `skills-runtime`（一个独立的 skill 执行运行时进程）隔离执行体，语义上类似 fork；实际隔离范围和启动代价仍要看宿主实现。

**Claude Code 的 inline / fork 是用户友好的显式 API**：

skill 作者一句 `context: fork` 就把执行环境定了。

**追问**: "fork 怎么传参？" fork 时把主 agent 的相关 context 包成 prompt 段。Claude Code 的 `Task` tool 接 `prompt` 参数。

**追问**: "fork 出来的 skill 怎么调 tool？" subagent 通常有自己的工具集合，且仍受 `allowed-tools`、宿主 policy、审批和 sandbox 约束；不能仅凭 SKILL.md 推断它一定能用或不能用主 agent 的工具。

<summary>**Q9 · 工程**：skill 调用 LLM 抽 trigger phrase 准吗？怎么提高准确率？</summary>

`when_to_use` 的具体程度可能影响 implicit invocation，但需要用带标签的请求集验证 precision、recall 和人工复核成本。

**手写 when_to_use 痛点**:

- 用户想不全 trigger phrase
- 同一 skill 多种用户表达方式
- 写得太宽 → 误触发
- 写得太窄 → 漏触发

**LLM 抽取方案**:

```python
def extract_triggers(skill_path: Path, sample_sessions: list[Session]) -> str:
    prompt = f"""
    Skill description: {skill.description}
    
    Sample sessions where this skill was useful:
    {format_sessions(sample_sessions)}
    
    Extract 3-5 trigger phrases that should make an agent invoke this skill.
    """
    return llm.complete(prompt)
```

**提高准确率的技巧**:

1. **正负样本**: 给 LLM 看「应触发」+ 「不该触发但相似」的样本对比
2. **eval 反馈环**: 跑测试 dataset，看 precision/recall，迭代 trigger phrase
3. **多模型 voting（待验证）**: 可让多个模型提出候选，再比较交集是否真的减少误触发
4. **用户 feedback**: 误触发时让用户标，加入负样本
5. **trigger phrase 分层**: 可把高置信触发 ("backport this fix") 和候选触发 ("apply to release") 分开，再用评测决定阈值

**Claude Code 的 eval 模式**:

源码注释里出现 `H1 ...` 这类标签，但没有公开完整样本、运行环境或汇总方法。它们是 prompt 字面量关联的 case-level 记录，不构成本站或跨产品 benchmark。

要复用这种思路，应保留每个 case 的输入、期望行为、运行版本和原始输出，再比较改动前后，而不是只抄一个分数。

**反例 · 不要这么做**:

- ❌ Trigger 写 "Use when user wants to do git stuff"（太宽）
- ❌ Trigger 写 "Use when user types exactly 'cherry-pick'"（太窄）
- ❌ 不带 example user message（模型猜）

**好例子**:

```yaml
when_to_use: |
  Use when the user wants to backport a fix to a release branch.
  
  Trigger phrases:
  - "cherry-pick X to release"
  - "backport this fix"
  - "apply Y to the release-N branch"
  
  Example user messages:
  - "Please cherry-pick commit abc123 to release-2.5"
  - "Backport the auth fix to last week's release"
  
  Do NOT use for:
  - Initial merge from feature branch to main
  - Squash-merging multiple commits
```

带正负样本，trigger 多种表达方式。

**追问**: "怎么测 trigger 准确率？" 先做一组带标签的请求，分别记录应触发和不应触发的样本，再统计误触发与漏触发。样本量、阈值和是否上线，要按产品的误触发成本与人工复核结果决定；本文不设统一数值门槛。

**追问**: "误触发怎么自动学？" 用户跳过 skill 的 session 做负样本入库。下次 eval 时把这些跑一遍看新版 trigger 还会不会误触发。

```python
DANGER_PATTERNS = {

def scan_skill(skill_path: Path) -> str:
    findings = []
    for file in skill_path.rglob("*"):
        ext = file.suffix
        if ext not in DANGER_PATTERNS:
            continue
        for pattern in DANGER_PATTERNS[ext]:
            if re.search(pattern, file.read_text()):
                findings.append("dangerous")
```

**Layer 6 · Implicit Invocation（可选 · 高级）**

```python
def detect_skill_to_invoke(user_msg: str, active_skills: list[Skill]) -> Optional[Skill]:
    candidates = []
    for skill in active_skills:
        if not skill.policy.allow_implicit_invocation:
            continue
        for phrase in skill.trigger_phrases:
            if phrase.lower() in user_msg.lower():
                candidates.append((skill, len(phrase)))
    
    if not candidates:
        return None
    return max(candidates, key=lambda x: x[1])[0]
```

**核心设计原则**:

1. **优先兼容公开的 SKILL.md 约定**: 先核对目标运行时，再决定是否扩展 frontmatter
2. **skill 数量变大时采用 progressive disclosure**: 列表只放元数据，正文按需加载
3. **先明确选择 inline 或 fork**: 两者的上下文、观察面和运行时边界不同
4. **scanner 只能覆盖已知规则**: 结合来源、人工确认和 runtime sandbox
5. **skillify 可降低沉淀门槛**: 但仍要让用户确认触发条件和持久化位置

实施范围和工期取决于现有 loader、运行时 policy、安装渠道与验证覆盖；本文不提供时间估算。

**追问**: "skill 跨 agent 怎么共享？" 只有在目标运行时接受相同 schema、正文格式和工具语义时才可能复用，兼容性需要逐项验证。

**追问**: "skill 怎么版本化？" SemVer + immutable distribution. 升级要重装。
